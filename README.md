# TagViewer (Electron + Vue 3 重构版)

WD14 标签可视化看板 —— 由原来的「Python `http.server` + 8 个手写 HTML 页面」重构为
**单进程 Electron 应用 + Vue 3 组件化前端**。

## 这个项目是干什么的

**一句话：把图片变成 tag 的「弹药库」，让 ComfyUI 抽卡越抽越自由。**

### tag 从哪来

两条路：一是**自己收集的图**——网上存的、别人分享的，AI 会自动「看图说话」反推出一套标签（WD14 反推）；
二是**自己用 AI 生成的图**，本来就带着生成时的标签。有意思的是：同一套标签抽十次卡能出十张不同的图——
同样的「蓝发、校服、教室」，姿势构图各不相同。挑出满意的那张再反推一次，就得到一套「进化过」的新标签。
这样一轮轮滚下去，标签库像滚雪球一样越滚越大。

### 导出：按需组合，不想要的 ban 掉

能导出的标签组合越丰富，抽卡的选择余地就越大。比如想要「举剑的骑士」，凭空想词很干瘪；
但库里存了二十张不同角度的骑士图，挑三张各导一份混着用，出来的图就丰富得多。
而且导出可以按需组合：导「萨菲娅」的标签时总带着「闭眼」，这次想画睁眼的，把 `closed_eyes` ban 掉，
导出时自动过滤；想要全身立绘就把「特写」类剔掉，想要大脸就剔「全身」，一个开关的事。

### 角色库与购物车：组队导出去抽卡

工具认得出每张图上画的是谁，自动把所有图按角色归好类——相当于白得一座按角色分好类的图库。
看图时看到喜欢的角色，点一下加进「购物车」，攒出一支想要的队伍：想画双人图就把两个角色丢进购物车，
一键导出成一个角色组文件，扔回 ComfyUI 直接抽卡。
**不同的角色组合 × 不同的标签组合，两个维度一乘，可能性就爆炸了。**

### 顺手的图片管理

全屏翻页看图、批量移动归档、按角色一键筛选，都是围着「服务画图」转的。

### 几个真正好用的细节

- **标签全带中文翻译**：内置 11,000 多条翻译，界面上所有标签都显示成「蓝发」「教室」，选词零门槛。
- **每个页面都有安全模式开关**：一键把不健康的图全藏起来，看板 / 收藏 / 购物车页页都有。
- **图片文件夹当「频道」管理**：每个文件夹一个按钮，点一下只看这个文件夹的图；
  移出来源就从界面消失（文件不动，可逆）。
- **整个作品的角色名单是现成的**：按「作品 → 角色」两级组织，支持中文搜索、批量入购物车。
- **小功能**：右键复制图片 / 用其他程序打开、收藏 + 备注、自动导出带倒计时、8 种排序、
  全程本地运行不上传。

## 路径与数据目录

全项目的路径解析只有一个真源：`electron/core/paths.js`（零 Electron 依赖，纯函数 + 调用方注入）。
其它模块一律从这里取，不再各算各的 —— 之前有 3 份等价的「默认数据目录」和 2 份日志目录实现，
改一处漏两处。

### 数据目录

| 优先级 | 来源 | 说明 |
|---|---|---|
| 1 | `settings.json` 的 `dataDir` | 真实设置文件在 `<userData>/settings.json`（Windows: `%APPDATA%\TagViewer\`） |
| 2 | 环境变量 `TV_DATA_DIR` | 适合脚本/多套数据切换 |
| 3 | `<userData>/data` | **新装机器的默认值**，一定是可写目录 |

数据目录里放什么，按「能不能对外分发」分三类（见 `paths.js` 的
`KNOWLEDGE_FILES` / `USER_FILES` / `DERIVED_FILES`）：

| 类别 | 文件 | 会不会随仓库分发 |
|---|---|---|
| **知识** | `local_translations.json`、`character_library.json`、`weilin_data*/` | 设计上可分发（不含图片），但**来源与授权需先核实**，当前一律不进仓库 |
| **用户数据** | `export_blacklist.txt`、`export_replace.txt`、`export_bg.txt`、`user_meta.json`、`cart_history.json`、`folders.json`、`safety_tags.txt`（安全模式的敏感标签集合，两段）、`safety.json`（开关与档位）、`.thumb_cache/` | **绝不出机器** |
| **可再生派生物** | `tags.db`、`scan_cache.json` | 不进仓库。都内嵌本机文件路径，将来若要随包分发必须先从里面**提炼**出纯标签/系列/角色子集 |

数据目录不存在时会自动创建。里面没有任何标签数据时，应用不会崩，而是显示
「还没有配置标签数据源」并告诉你把 `tag_viewer_config.json` 放哪（见 `TvBootOverlay`）。

### 数据源：真源是 `tags.db`，不是 txt

**一句话**：`tags.db` 的 `folders` 表是「有哪些目录、它们各自的用途」的唯一真源；
`tags_*.txt` 与 `scan_folders.json` 都已降级为**一次性的导入介质 / 可导出的备份**。

```
磁盘目录 ──(登记)──> folders 表 ──(增量同步)──> images 表 ──> 界面
                        ▲                          ▲
              「来源管理」页可增删改          tags_*.txt 只是首次导入的来源
```

`folders` 表里三个独立开关决定一个目录的用途：

| 开关 | 含义 | 图片去哪 |
|---|---|---|
| `as_source=1` | **看板来源** | 进 `images`、进统计、可被搜索 |
| `as_scan=1` | **扫描夹** | 只在扫描页浏览，**不进库** |
| `auto_tag=1` | **自动反推**（默认开） | 只对「来源」有意义：**刚被登记为来源**那一下自动补一次增量同步，跑完接着排上 WD14 反推（详见 2026-09-23 那节） |
| 前两个都是 0 | 已移出登记表 | 行还留着，开关打回来即可恢复（库里的记录一条不掉） |

**看板上「有哪些来源」= 登记表里 `as_source=1` 的那些目录**，而来源名（那颗胶囊上的字）是
`label || 文件夹名` —— `label` 留空是合法状态（扫描页「添加文件夹」就不传它），此时用文件夹名。
详见下面「来源名与移出来源」一节。

**把 `as_source` 关掉 = 那个目录的图从看板隐藏**（不是删）：`readRecords` 会跳过 `as_source=0`
的目录下的图，于是「全部」的数字跟着掉、它的胶囊也消失；**`images` 表一行都不动**，打回开关
立刻全回来。这就是「移出」与「彻底清除」的区别：前者可逆、后者才真删库里的记录。

**目录已经不在磁盘上时，`as_source` 应当关掉。** 看板的可见性只看 `as_source`、**不看磁盘** ——
留着 `as_source=1` 它就会照样渲染那些文件，缩略图请求全变 404（本机实测 96 条，把
「运行期无 JS 异常」顶红）。移出登记**只注销用途、行保留**，所以关掉它不丢任何记录。

同一个目录可以两个都开（如既是来源又是扫描夹）。「只看 AI 新生成图」这类目录应当
**只开扫描夹** —— 它不该被追平进标签库。

**怎么加/删来源**：顶栏 →「🗄️ 来源」。添加即登记 + 扫描；「移出」只注销用途（可恢复）；
「彻底清除」才会连库里的图片记录一起删（高危，需二次确认，磁盘文件始终不动）。

#### `tag_viewer_config.json` 现在是什么

数据目录下的 `tag_viewer_config.json`，模板见 `data/tag_viewer_config.example.json`。
这个文件允许 `//` 整行注释。三个来源字段（`data_files_dir` / `data_files` / `data_file`）
现在只用于**首次灌库**：库里已经有数据之后，它们不再决定「有哪些来源」。

- 配置里的 `tags_*.txt` 若指纹（size + mtime）没变，启动时是**空转**，一行都不读；
- 配置读不出来（文件丢失/损坏）时得到一个空数据源 —— 此时应用继续从 `tags.db` 读，
  **并且不会把库里已有的来源和图片删掉**（这条有专门测试守着，见 `test:db-safety`）；
- 把 `tags_*.txt` 全部移走也是安全的：来源集合为空时同步直接早退，一个字节都不动，
  而来源列表读的是 `folders` 表，所以界面上的来源一个不少。

> ⚠️ **要移走 `tags_*.txt` 就必须 9 个一起移**，不能挑着移。原因见
> `docs/数据源合并与增量入库方案.md` §5.4：旧的 `syncSources` 会把「配置里已拿掉的
> 来源」从库里 DELETE，只移一部分会让剩下那些 txt 对应的来源被清理掉。
>
> 归档有现成命令（**默认干跑**，只报告不动文件；它会先把每个 txt 与库逐项对账，
> 对不上就拒跑）：
>
> ```bat
> npm run txt:archive          :: 干跑：列清单 + 与库对账
> npm run txt:archive:apply    :: 整批改名移进 _legacy_归档_<日期>/（可还原）
> npm run txt:archive:undo     :: 整批移回原位
> ```
>
> 归档是**同目录改名移动**，不删字节；归档目录里的东西要不要删由你自己决定。

`folders.json`（旧名 `scan_folders.json`，由 `paths.js` 路由到 `data/user/`）
只是登记表的**导出备份**，用 `npm run folders:export` 生成，随时可以重新导出；
真源丢了也不会因此丢来源。

翻译库（`translate_dir`）是另一条独立的解析规则，**默认留空就行**：

| `translate_dir` | 行为 |
|---|---|
| 留空 `""`（推荐） | 自动在数据目录下找 `weilin_data*` —— 把翻译库整个丢进数据目录就能用，不必写绝对路径 |
| 填绝对路径 | 用指定的那个目录；**路径失效时会自动回落到上面的自动发现**，并在 `launch.log` 里记一条 `warn` |
| 两种都找不到 | 不启用翻译，界面只显示英文标签（不会崩） |

`weilin_data*` 被 `paths.js` 归为「知识目录」（`KNOWLEDGE_DIR_PREFIXES`），
所以放在数据目录里就等于被认领 —— 这也是它跟 `local_translations.json`、
`character_library.json` 一样被 `.gitignore` 排除、只随「知识包」分发的原因。

每次启动都会在 `launch.log` 里留一行翻译库的实际加载结果，例如：

```
[ok] 翻译库: WeiLin 7540 条 + 本地补译 4072 条 = 11580 条 · 来源=数据目录自动发现 · dir=...\data\weilin_data(...)
```

WeiLin 读到 0 条、或配置里的路径不存在，这一行会变成 `[warn]` —— 这样「翻译整体消失」
就不用靠肉眼去发现了。

### 日志

| 场景 | 日志目录 |
|---|---|
| 开发期（`npm start` / 双击启动脚本） | `<仓库>/logs/`，写 `launch.log` 与 `ready.flag` |
| 打包后 | `<userData>/logs/` —— 打包后 `__dirname` 在只读的 asar 里，项目内 `logs/` 写不进去 |
| 覆盖 | 环境变量 `TV_LOG_DIR`（语义是**目录**） |

两个启动脚本靠 `<仓库>/logs/ready.flag` 判断「窗口是不是真的起来了」，所以开发期这条路径不能变。
渲染进程的报错会经主进程转发进同一份日志（`[render]` / `[ipc-err]` 前缀）。

### 本机专属配置

开源后仓库里不能出现任何开发机的绝对路径。凡是「只有这台机器才成立」的值，
写进 `local.config.json`（**已被 `.gitignore` 排除**，模板见 `local.config.example.json`）：

| 键 | 用途 | 等价环境变量 |
|---|---|---|

### 技术要点
- **数据目录可配置**：黑名单、替换规则、收藏备注、购物车历史、翻译库、`tags.db`、
  缩略图缓存都放在同一个「数据目录」里。解析优先级：
  `settings.json` > 环境变量 `TV_DATA_DIR` > `<userData>/data`（新装机器的默认值）。
  详见下方「路径与数据目录」。
- 标签数据会**导入一份 SQLite 库**（`tags.db`，在数据目录下）当索引用 ——
  首轮导入一次，之后靠指纹跳过。**库现在是唯一真源**（`folders` 表管「有哪些目录、
  各自什么用途」），`tags_*.txt` 已降级为一次性的导入介质 / 可导出的备份。
- 运行时**不再需要 Python**：原来的 22 个 HTTP 端点全部变成 IPC channel。
- **图片与元数据彻底分离**：图片始终留在你自己的磁盘上，应用只读本机文件、
  不做任何上传。设计上可对外分发的是「知识」（标签翻译 / 系列角色映射），不含图片；
  当前仓库里**一个数据文件都没有**（见 `.gitignore` 的说明与 `data/*.example.json` 模板）。

## 功能演进日志（按改动时间记录 · 原文未改，只挪了位置）

### 2026-09-18 三项优化

#### 1. 大图预览：滚轮翻页 + 点空白关闭

旧版要点开下一张必须「关掉 → 找图 → 再点」，看一批图就是几十次点击。

| 交互 | 实现要点 |
|---|---|
| **滚轮 / 触控板上下滑** | 累计 `deltaY` 到 55px 才切一张，切完进 190ms 冷却。**不能按事件直接切** —— 触控板一次滑动会连发几十个 `deltaY≈3` 的事件，那样会"飞"过去。停手 120ms 没攒够就清零 |
| **点图片区任何空白** | 关闭（`.lb-img-wrap` 整片，含图片本身）。侧栏 `@click.stop`，因为那边要点标签 |
| **← / → / PgUp / PgDn** | 翻页；**Esc** 关闭。光标在输入框里时不抢键 |
| **点遮罩边缘 / ✕** | 关闭 |
| **底部「‹ n / m ›」** | 显示当前位置，箭头可点；不在列表里（库外图）就整块不显示 |
| **左右浮动大箭头** | 到首/尾自动禁用 |

翻页的前提是知道"当前这批图是什么"。所以 `lightbox.open(path, { list })` 新增第二个参数，
各页面把 `feed.items.map(i => i.path)` 传进去；翻页时**按 path 而不是下标**做竞态保护 ——
切图快时慢请求回来会覆盖新图，`load()` 里比对 `path.value !== p` 就丢弃过期结果。

**顺手补的一个显示问题**：外部图片的 ban 命中。实测扫描页的库外图 0% 命中黑名单是**正常的**
（它们的标签来自画师自己的 PNG 元数据，跟库内 71k 张不同源；库内约 25% 命中），
但界面上「没有提示」和「没适配」长得一样。现在光箱里显式给出两种状态之一：
`🚫 命中黑名单 N 个` 或 `✅ 本图无标签命中黑名单`，前者 hover 能看到具体是哪几个词。

**标签上的三个动作**（2026-09-20 调整）：

| 点哪儿 | 做什么 |
|---|---|
| 标签本体 | **打开"这个标签的图片"子页面**（`/tags/:tag`）—— 与"标签页里点标签"是同一个入口 |
| hover 展开的 **📋** | 只复制这一个标签（原来是点标签本体就复制） |
| hover 展开的 **🛒**（仅角色 pill） | 加入 / 移出购物车；已入车时常驻高亮 |
| hover 展开的 **🚫** | 切换黑名单 |

图标平时**整体隐藏**，悬停时以**浮层**形式从右侧滑入、盖在 pill 自身右段上方 ——
浮层是绝对定位、**完全不占布局宽度**，所以悬停不会改变 pill 几何、不会把行尾的
pill 挤到下一行（内联 `max-width` 展开版会触发"换行 → hover 丢失 → 弹回"的抽搐
死循环，2026-09-20 已根治）。已 ban 的 🚫 与已入车的 🛒 例外：改为**内联静态**
常驻（静态宽度不随悬停变化，同样不会抽搐）。光箱与详情页两处行为统一。
**库外图片**（扫描夹里的那些）点标签会额外给一句提示：它自己不在标签库里，
跳过去看到的是库里含该标签的图。

**复制按钮收成一个下拉**（2026-09-20）：光箱的「复制全部标签 / 去ban / 含角色」与
详情页的「复制全部标签 / 去ban复制」合并为 `TvCopySplit` —— 主按钮按**当前模式**
复制（label 显示模式名），右侧小箭头展开菜单换模式；**菜单项点击 = 切到该模式并
立即复制**。收藏按钮保持独立。

**落点是标签列表的下一级子页面**（2026-09-20 改）：地址写成 `/tags/:tag` 而不是
`/tags?tag=xxx` —— 层级体现在地址栏里，面包屑是「全部标签 > 该标签」，点它一步回到
列表；**浮动返回键从哪来回哪去**（2026-09-20 第四轮改）：从光箱点标签跳过来的，
返回会回到来源页并把光箱恢复出来（定位到当时那张图、翻页列表也在）；从详情页跳来
的就回详情页；深链直接进来（history 没有上一页）才回标签列表。面包屑「全部标签」
和「← 返回标签列表」按钮保持字面行为不变。
标签名里的 `/`（如 `bb_(fate/extra)`）由 vue-router 编成 `%2F` 再解回，不会被拆成两段路径。
旧地址 `/tags?tag=xxx` 由路由 `beforeEnter` 重定向过来，老书签照旧能开。

#### 2. 扫描页 → 文件夹库（两级）

原来每次都要「重新选目录 / 重新粘路径 → 扫描」，目录一多就是体力活。

```
文件夹卡片列表                    ┌ 点进去 ─┐             图片网格(二级)
[📁 涩一点点]  [📁 ai图\26_09_18]  ──────────→   面包屑 ‹ 全部文件夹 / 涩一点点
 含提示词 412 · 8 种提示词 · 封面            共用基础标签 2 个: 1girl, halo
 ✏️ 改名  🗑 移除 ← hover 才出现             [缩略图网格, 点开进大图预览]
```

- 索引落在数据目录的 `scan_folders.json`（`electron/core/folders.js`）。
  **只存路径 + 上次统计 + 封面，不存图片清单** —— 清单可能几千条，又大又容易过期；
  点开时现扫，且 `scan.js` 有内存缓存，第二次点开是秒开。
- 粘贴路径回车 = 添加（自动扫一遍并入库）；同一路径重复添加 = **刷新**，不会产生第二条。
- 移除记录**只删记录，绝不动磁盘上的文件**。
- 路径不存在时卡片标「路径失效」，不会崩。
- **二级页支持按标签筛选**（2026-09-20）：网格上方的搜索框输入标签名即可，
  空格分隔多个 = AND（同时满足）。因为是**前端过滤**，输入即时生效、不重扫文件夹；
  筛完之后打开大图预览，翻页序列也只包含筛出来的那些图。
  补全走**这个夹自己的标签池**而不是标签库 —— 扫描图是库外的，它们特有的标签
  在库里根本查不到；顺带支持中文（输「星野」能补出 `hoshino`）。
  多词无交集时给明确空态，浮动返回键会先清筛选、再按一次才回文件夹列表。
- **同一个筛选框也认文件名**（2026-09-29）：每个词**标签或文件名（含扩展名）命中其一即算**，
  大小写不敏感、子串匹配；空格分隔多个词仍然是 AND（只加了一条通路，没动分词规则）。
  为什么加：扫描夹里常有一批**裸图**（PNG 里没提示词、标签也反推不出来），
  想在其中定位某一张，唯一的抓手就是文件名 —— 搜 `a3` 要能直接出 `a3.png`。
  注意**补全仍然只认标签池**（文件名压根不在标签库里），所以敲文件名时下拉会显示
  「没有匹配的标签（文件名仍会匹配）」—— 这不是矛盾，是两件事各说各的。
  当前行为的实测锚点（夹具 `a1..a5`）：`a3`→1 张 · `A3`→1 张 · `a1 hoshino`→1 张
  （一个词走文件名、一个走标签，仍 AND）· `a1 a5`→0 张（多词是 AND 不是 OR）·
  `.png`→5 张 · 无命中→空态。
- **筛选框的历史是独立的一份**（2026-09-20）：存 `tv_search_hist_scan`，
  与首页搜索框那份 `tv_search_hist` 完全分开 —— 一边是"敲过的查询"、一边是"筛过的标签"，
  混着存两边都变脏（首页搜过的词会跑进筛选框的下拉，反之亦然）。下拉里那行小标题
  也各自写明是哪一份，用户看得出它们不共享。
  筛选是**即时**的、没有搜索按钮，所以记历史的时机是"输入停稳 1.2s"（而非提交时）。

#### 3. 标签数据落 SQLite

> 📌 这一节记录的是 **2026-09-18 当时**的形态。此后 `tags.db` 已经从"索引"升级为

### 2026-09-22 导出预设（ban 完自动导出）

**痛点**：每 ban 一个词条都要手动点一次导出、再在「另存为」里挑目录 —— 一天几十次纯重复劳动。

**做法**：把「筛选条件快照 + 目标目录/文件名」存成**预设**，黑名单**内容真的变了**就自动覆盖导出一次。

| 设计点 | 为什么这么做 |
|---|---|
| 触发只认**黑名单内容指纹**(sha1) | 打开编辑器原样保存、连点多个 🚫，都只导一次；不会因为"点了保存"就白跑 |
| 1.5s 防抖合并（2026-09-24 起改为**可配、默认 3 分钟**） | 连续 ban 一批词条只导一次，不是每个词条导一次（详见下一节） |
| 写入走**临时文件 + rename 原子替换** | 下游（ComfyUI 等）固定读这个文件，绝不能读到写了一半的内容 |
| **rename 要退避重试** | Windows 上刚写出的 42MB 文件会被 Defender/索引器短暂占住，一次 `EPERM` 就把整次导出丢掉（详见下面第 7 个坑） |
| 预设存 `user/export_presets.json`（走 `dataFile` 路由） | 含本机绝对路径，属"用户数据"，不进仓库、e2e 沙箱另有自己的一份 |
| 导出失败**绝不影响 ban** | ban 是主操作、导出是附带的；失败只记进预设的 `lastError` 并回执给界面 |
| 数据集没就绪时**不导**，但**就绪后补跑** | 半份数据不能覆盖上一次的好结果；但"挡掉就永远不补"会让这次改动白改 |
| 关窗前把待导出的**立刻跑掉** | ban 完最后一个词条马上关窗口，延迟还没到期 —— 不跑就白按了（2026-09-24 起改成"取消定时器当场导"，原先是"等它到期，最多 8 秒"） |
| 界面载荷统一过 `api.js` 出口的 `toPlain()` 深拆 | Vue 的 `reactive`/`ref` 取出来的是 **Proxy**，直接递过 IPC 桥必抛 `An object could not be cloned.`（详见第 9 个坑） |

界面入口在首页导出区：`📤 预设导出 · 自动 N`（N = 已开启自动导出的预设数）。
列表里能单独开关「变更后自动导出」，也能「立即导出」验一次。
**2026-09-24 起角标还会变成「待导出 mm:ss」倒计时并可以点**（点一下跳过等待立刻导）。

> 「在界面上点💾创建预设」这条路径由 e2e 单独断言覆盖（`导出预设(界面):` 那 6 条）。
> 这不是重复劳动：只打 `window.tv.invoke` 的断言**永远测不到它** ——
> 那条路压根不经过 Vue 的响应式状态，第一版就是因此带着 bug 全绿发布的。

#### 首页动作区的三层结构

侧栏底部原来是 **6 个等宽按钮摊成两排**，谁高频谁低频完全看不出来。现在按「这是什么性质的东西」分三层：

| 层 | 元素 | 为什么在这一层 |
|---|---|---|
| 1 | `🔍 搜索`（独占一行、primary） | 唯一的高频「动作」，不用跟别人抢注意力 |
| 2 | `⬇ 导出标签` + `▾`（分裂按钮）、`🚫 黑名单` | 导出高频但只有一个变体常用；黑名单在 ban 循环里也高频，留在明面上 |
| 3 | `🔁 替换规则`、`📤 预设导出 ③`（ghost 小按钮） | 它们是「进去配置」的入口，不是对当前结果的动作 |

三处合并/降级：

- **`⬇ 导出(带路径)` 并进 `▾` 下拉** —— 它和 `导出标签` 是同一个函数（`doExport(withPath)`），只差一个 `with_path=1`。
- **两个导出开关从筛选区搬进下拉**：`导出剔除角色/系列标签`、`缺背景时补背景标签` 都**不进 `buildQuery`**，只影响导出结果。留在筛选区会让人以为它们也在过滤视图。
- **底部 tip 里原本还挂着「黑名单/替换/预设导出」三个超链接**，与按钮完全重复 —— 已删；说明文字改挂到各按钮的 `title` 上（悬停可见，不占版面）。

两个实现上的坑：

- **下拉挂在「整排」上，不挂在分裂按钮上。** 按分裂按钮宽度算只有半排宽，说明文字与复选框 label 立刻被挤成两三行（第一版实测如此）。定位上下文得是 `.brow`。
- **下拉向上开。** 动作区在侧栏底部，往下会撞上 `.left` 的滚动裁切；箭头跟着翻转，免得方向感对不上。
- e2e 里**不点**下拉里的两个导出项 —— 它们会走 `dialog.showSaveDialog`，原生模态框在 e2e 里没人关得掉，整轮挂死。那 6 条 `首页动作区:` 断言只保证「入口在、文案对、开关绑着、展开不裁切」；`with_path` 的语义由 `selftest.mjs` 覆盖。

### 2026-09-24 导出延迟可配（默认 3 分钟）+ 待导出倒计时

**痛点**（用户原话）："点击黑名单后过几分钟再自动导出，因为有可能同时 ban 好几个，每个都导出有点耗时"。

1.5s 防抖只能合并"同一瞬间"的连点；真实操作是隔几秒 ban 一个、连着 ban 十几个，于是**每个都各触发一次完整导出**。而一次导出是**主进程同步**的 3~4 秒（实测 81,955 行 / 40.1 MB，两个预设合计 7.7s）——用户感受到的是"每 ban 一下就卡一下"。

| 设计点 | 为什么这么做 |
|---|---|
| 延迟**全局一个值**、存 `export_presets.json` 顶层 `autoDelayMs`，默认 **180000** | 用户要的是"一批改动合并成一次"，不是"每个预设各等各的"。档位 `1.5s / 30s / 1min / 3min / 5min / 10min` 白名单化 —— 这个值落在能手改的 json 里，乱值一律退回默认 |
| 排程状态机摘成 `electron/core/exportScheduler.js`（纯逻辑、依赖注入） | 才能用**假时钟**把 3 分钟在一毫秒里跑完：`scripts/test-export-presets.mjs`（17 条，不启 Electron、不碰真实库） |
| 延迟期间侧栏角标显示「待导出 mm:ss」，**点一下立刻导** | 等几分钟与"功能坏了"在界面上长得一样。倒计时在渲染层本地走（主进程只推一次 `scheduled`），3 分钟不用叫醒 180 次 |
| 复用的推送仍是 `export:auto`，加 `kind: scheduled / result` | 不新增推送通道 —— `preload.cjs` 的 `PUSH` 白名单漏加一处会**静默返回空退订函数**，是踩过的坑 |
| 只在**一批的第一次**排程时提示一次 | 连 ban 十几个不该刷十几条 toast（`fresh` 字段由排程器给出） |
| e2e **自己调接口**把延迟设成 1.5 秒（导出的第一件事，带断言） | 否则"ban 之后等它自动导出"的断言要干等三分钟。**没用环境变量**：`TV_EXPORT_DELAY_MS` 那种"env 永远优先"会让界面开始骗人 —— 弹窗按存档值显示"3 分钟"、实际按 env 导，而且改延迟永远不生效（第一版就这么错了，两条断言挂得莫名其妙） |

顺带修掉两个真问题：

1. **正在导出时又 ban → 这次改动永远不会落地**（旧代码 `runAuto()` 开头 `if (running) return {skipped:true}`）。没有提示、没有痕迹，用户以为导过了而文件是旧的。延迟改成几分钟后撞上这个窗口的概率大增。现在：标 `dirty`，跑完自动补一轮（**补跑也走正常延迟**，不是立刻连跑两次）。
2. **关窗前把待导出的立刻跑掉**。旧实现是"等排程到期，最多 8 秒就退出"—— 延迟 3 分钟后必然超时，等于 `ban 完立刻关窗口 = 白改`。现在 `before-quit` 取消定时器、当场跑完再退（代价是关窗口可能多等几秒，这是刻意的）。

界面：`📤 预设导出` 弹窗列表态顶部多一行「ban 完之后等 [3 分钟] 再自动导出」，改完**立刻生效**（正在等的那批会按新时长重排）。

> 明确**没做**：导出仍是主进程同步执行（大库一次 3~4 秒界面会卡）。延迟合并已经把"每 ban 一次卡一次"变成"一批卡一次"，真要治得把导出搬去 worker/子进程，属另一条线。

验证：`npm run check` + `npm run test:presets`（17 条，含负向对照：把排程器退回旧语义，"补跑"那条**必红**——已实测）+ `npm run e2e -- --no-shot`。

### 2026-09-29 购物车自动导出（购物车一变就导一份，不用再「另存为」）

**痛点**：购物车导出每次都要走「另存为」挑目录、挑文件名，而下游 ComfyUI 读的是**固定路径**的 wildcard 文件 —— 挑来挑去挑的是同一个地方。

**做法**：一份**独立于「导出预设」的单预设**（用户明确说"这个预设只需要一个"）：存好【目标目录 + 文件名 + 延迟】，购物车**内容真的变了**就按延迟覆盖导出一次。内容与「导出全部」逐字一致（同一个 `buildCartExport`）。

| 设计点 | 为什么这么做 |
|---|---|
| 触发挂在 **`useCartStore` 的 watch** 上（每次变更把 tags 全量报上去），不是逐个入口挂钩子 | 购物车有**六个**改动入口：标签详情页「角色」区 pill / 光箱 pill / 系列页卡片与批量加入 / 购物车页与抽屉的删除清空 / 结算后自动清空 / 历史载入整体替换。挂 store 一次全覆盖，以后加新入口也不会漏 —— 漏挂的症状是"从某个入口加的角色永远导不出去"，界面上毫无异常 |
| **清空不算"更新"**，不导、也不排程 | 结算是「导出 → 存历史 → 清空」，若把清空当更新，就会**把下游那份文件悄悄清成空** —— 而刚结完的那批可能还在被 ComfyUI 使用。顺带一个好处：清空后把同一批加回来时指纹与上次一致，判定为"没更新"，不白导一遍 |
| 判定用**顺序敏感**的指纹 | 导出文件是按 `list` 顺序逐行写的，"移出再放回来"会让行序变化，那就是内容真的变了 |
| 只有**打开开关 / 换目录**时立刻补导一份 | 否则用户对着一个空目录等 30 秒，或者以为"开了开关文件就有了"。日常改动才走延迟 |
| 延迟是**这个预设自己的**（存 `cart_preset.json`），默认 30 秒 | 与黑名单那条各存各的：只有一个预设，那它的延迟就是它的属性，不该再多一个全局旋钮让人搞混"我改的是哪个" |
| 关窗前 `before-quit` 也会把它排程中的那次跑掉 | 加完角色就关窗 = 延迟还没到 = 等于没开这个功能 |
| 排程器**自带一份精简版**（`cartPreset.js` 里），没有复用 `exportScheduler.js` | 那份当时属于另一条**还没提交**的工作线，引用它会逼着把半成品一起提交。语义照抄（idle/scheduled/running + dirty 补跑），等那条线落地后两边可以合并成一份 |

界面入口两处（同一个面板组件，不会漂移）：购物车页 / 抽屉的 **`⚙ 自动导出`** 按钮（带状态点：绿 = 已同步，橙 = 有更新还没导出去），以及 `📤 预设导出` 弹窗里内嵌的「购物车自动导出」区块。

预设存 `user/cart_preset.json`（走 `dataFile` 路由，含本机绝对路径 → 属"用户数据"，不进仓库、e2e 沙箱另有自己的一份）。

验证：`npm run test:cart-preset`（28 条，纯 Node、假数据目录：指纹/清空/顺序/防抖合并/开关补导/手动导出/脏 json 容错）+ `npm run e2e`（真实界面走两条入口：购物车页删一条、**标签详情页角色 pill 的 🛒**）。

### 2026-09-23 改来源自动接同步 + 反推（把 `auto_tag` 这个预留位接上）

**痛点**：在扫描页加完文件夹、再去来源页把它登记为「来源」，界面上一路都正常 —— 但**一张图都没进库、反推队列恒为空**。当时以为是"设计如此"，其实是三条路各断各的：

| 环节 | 代码 | 实际行为 |
|---|---|---|
| 扫描页「添加文件夹」 | `folders:add` → `addFolder` | `scanFolder` 只枚举文件 + 写扫描缓存，**从不写 `images` 表**；落库 `as_scan=1, as_source=0` |
| 来源页「改来源」 | `folders:update` → `updateFolder` | 是**同步函数、纯 DB 打补丁** —— 它根本不知道 ingest 存在 |
| ingest 的入口 | `ingest.js` 的 `WHERE as_source = 1` | 只遍历**来源**目录；且 `scheduleIngest()` 带一次性标志，**每次启动只自动跑一次** |

也就是说自动链条（`onIngestDone → scheduleTagging → runTagOnce`）本身是通、也接对了的，只是**没人踢第一脚**。

**做法**：`folders:update` 从「纯打补丁」改成识别**跃迁** —— `as_source` 由 `0→1` 那一下，自动为该目录跑一次 `runIngest({only: id})`，跑完走既有的 `onIngestDone`（重载数据集 + 把反推排上）。

| 设计点 | 为什么这么做 |
|---|---|
| 只认**跃迁**（`prev.as_source === false && folder.as_source === true`） | 只看改后的值分不出"刚被登记"和"本来就是来源、这次只改了别的字段"；后者再同步一遍纯属白扫盘。为此 `updateFolder` 新增返回 `prev`（改前装饰快照） |
| `folders.auto_tag` 做**单目录开关** | 这个字段建表时就有、此前**全仓库只读不写也没有任何消费点**。正好是这个位置预留的；关掉即只在你点「同步」时跑 |
| **尊重 `TV_INGEST=0` 总闸** | 自动行为绝不能在测试/dev 里偷偷去 stat 用户真实盘符上的几万个文件 —— 那正是 `electron-path.mjs` 默认关它的原因。**这条同时也是这条链路能被 e2e 覆盖的前提** |
| **绝不 `await`** | 首次同步要枚举目录下全部文件（分钟级），挂着等会把「改开关」这个动作卡死。改开关**立刻返回**，并附一个 `autoSync` 判定回执（`wanted` / `started` / `reason`）供界面与断言用 |
| 界面第三个开关非来源时**置灰但仍渲染** | 保持每行是同一套固定面板，不随状态忽隐忽现（e2e 也就能数固定条数） |
| `.uses` 列宽 190px → 240px | 三个开关横排约需 231px，不放宽会溢出到相邻列 |

> 注意语义：只有「库里没有 + 图内**也没有**元数据」的裸图才进 `tag_queue`。带元数据的 ComfyUI PNG 不进队列，此时反推静默无动作是**正确**行为，不是 bug。

### 2026-09-23 来源名与「移出来源 = 从看板隐藏」

用户报的两个现象，看着不相关，其实是**同一个键**上的两个断口：看板的「来源条」是按
**来源名**分组的，而来源名在库里就是 `folders.label`。

| 现象 | 根因 |
|---|---|
| 新登记的目录（`表世界`）看板上**没有它的胶囊**，它的 2970 张图挤在一个「名字为空串」的分组里 —— 计进「全部」，却筛不到也藏不掉 | `folders.label` 是**空串**（扫描页「添加文件夹」不传 `label`；界面上那个名字是 `decorate()` 用 `basename` 临时合成的，**所以 DB 里的空值在界面上看不出来**）。而 `sourceNameList` 的 SQL 写的是 `AND label <> ''` —— 被静默滤掉 |
| 已经移出来源的目录（`桌面壁纸`）仍以来源身份留在来源条上 | `sourceNameList` 末尾的 `src` 表兜底把 txt 时代的名字**无条件**补了回来，完全不看 `as_source` |

**修法一：来源名两侧同口径。** 新增 `folderBaseName(path, label) = label || 文件夹名` 与
`folderNameMap(db)`（**一次算全表**），`sourceNameList()` 与 `readRecords()` 共用它。
- 必须共用一份：这两处分别在算「有哪些胶囊」和「每条记录属于哪个胶囊」，算法一旦分叉，
  `record.source` 就对不上任何胶囊名，图又变回隐身。
- 必须算全表：重名要消歧（`x/桌面壁纸` 与 `x/桌面壁纸/桌面壁纸` 的 basename 都是「桌面壁纸」），
  先缀父目录名、再撞就缀 id —— 来源名是筛选的键，重复键会让两批图共用一个胶囊。
- 读侧兜底意味着**不需要迁移**：库里已经趴着的空 `label`（如 `表世界`）当场就修好了。

**修法二：`as_source` 同时决定「看不看得见」。** `readRecords` 的 WHERE 收窄成
`gone=0` **且**目录不是 `as_source=0`（`folder_id` 为 0/NULL 的 txt 遗留记录不受影响）。
- 一行 `images` 都不改，所以是**非破坏、可逆**的：打回开关立刻全回来。
  用 `gone` 去做这件事会与「文件真的不见了」那套语义打架，所以没走那条路。
- 顺带把 `src` 表兜底加了个守卫：只补**还有可见记录**的老来源 —— 否则会留下一个
  「胶囊在、点进去 0 张」的空壳（`桌面壁纸` 就是被它复活的）。

**顺带修的认知差**：扫描页卡片上那行「含提示词 N」是**图里嵌的元数据**，而 WD14 反推
**只写库、不写回 PNG**（`tagger.js` 全程只 `applyTags` 到 `images.tags`）—— 所以一批裸图
反推跑完，扫描页看着还是"没有标签"。卡片现在多一行「库内 N 张 · 已反推 M」，两者分开显示。

**修法三（第三个断口，也是顺带发现的）：扫描页的文件夹列表是"陈旧"的。**
`ScanView` 在 `App.vue` 的 KeepAlive 白名单里，`loadFolders()` 只挂在 `onMounted` ——
而**一辈子只 mount 一次**。于是「在来源页把某个目录勾成扫描夹 → 切回扫描页」看到的还是老清单，
用户视角就是"我加了、它没反应"。现在 `onActivated` 会重查一次（首次激活跳过，因为紧跟
`onMounted`）。`loadFolders()` 是整体替换 `folders.value`，不动 `level`/分页/滚动，代价只有一条查询。

**沙箱这边的镜像问题**：`harness` 每轮复位登记表时也犯了同一个错 —— 只按 `src` 名单
把来源打回，**不看那个目录还在不在磁盘上**，于是用户早已移走的 `桌面壁纸` 每轮都被复活，
它那 7751 行死图的缩略图 404 把「运行期无 JS 异常」顶红 96 条。规则已改成逐行判定
（细节见下面「测试是幂等的」那一段）。

### 2026-09-23 图片真实比例 + 自适应行高 + 安全模式

三件事都是**读侧**改造，共同点是"不再凭空假设"：卡片以前不管图是横是竖一律按 9/16 渲染；
排布以前是 CSS grid 按行对齐（一行的高度取最高的那张，横图下面必然空一片）；
内容是否敏感以前根本没有判据（库里**没有** `rating_*` 标记，实测 0 张）。

#### 1. 卡片按图片真实像素比渲染（横图不再被裁成竖条）

**根因**：卡片容器写死 `aspect-ratio: 9/16` + `object-fit: cover`，横图被裁成竖条。
而且这**不是边角情况** —— 实测库里横图 **14,136 张**（占已回填尺寸的 18%），
而 `垃圾桶` / `新世界` / `里世界` / `表世界` 那几个壁纸来源**百分之百是横的**（合计约 1.4 万张，
也就是说横图基本就是这几批）——它们以前全被裁成竖条。

**做法**：把尺寸存进库，卡片按它算比例。

| 环节 | 落点 |
|---|---|
| 读尺寸 | `electron/core/imgsize.js` —— 只读**文件头**（PNG / JPEG / GIF / WEBP / BMP），**不解码整图**。先读 4KB，只有 JPEG 还没找着 SOF 才补读到 64KB（实测与"一次读 64KB"结果逐字节一致，但快得多）。认不出一律返回 `null`，**绝不猜** —— 猜错比不渲染更糟 |
| 存尺寸 | `images.px_w` / `images.px_h` 两列，加在 `store.js` 的 **`ADDITIVE_COLS`** 上（每次 `openDb` 都会补，**不需要迁移**） |
| 回填 | 两道：① `npm run backfill:dims`（老库一次性补齐，默认干跑）；② `ingest` 每轮懒回填，`DIM_FILL_MAX = 30000` 张/轮，不用手动跑 |
| 渲染 | `ratioOf(px_w, px_h)` → `aspect-ratio: W / H`；**0 = 未知**，回落 9/16（=改动前的行为） |
| 系列封面 | `query.js` 的 `coverIdx()` 取代 `minIdx()`：谁的长宽比离容器 `3/4` 最近谁当封面。竖图天然更近，所以"优先竖图"不需要额外特例；同分取下标最小的，保证封面稳定、不会每次请求换一张 |

实测回填成本（85,558 行）：**冷跑 957 秒**（磁盘 I/O 主导），文件进了系统缓存后**同样规模 15 秒**。
命中率 90.8%；"读不到"的 9.2% 里绝大多数是用户早已移走的那批（`桌面壁纸` 一个来源 7,747 行
100% 不在磁盘上），真实缺失只有约 0.1%。

**2026-09-23 复核**（把真实库复制一份出来、只读统计）：`images` **85,796 行**，已回填
**77,959**（90.9%）；`NULL` 7,832、`px_w=0` 5 行、`gone=1` 85 行。关键一条：
**7,832 个 NULL 里 7,747 个就是 `桌面壁纸` 那批** —— 目录早被移走、文件不在磁盘上，
读不到尺寸是**应该**的。也就是说"缺尺寸"实际只落在**死记录**上，在册的图基本都量到了，
卡片按真实比例渲染对用户是完整生效的。

#### 2. 自适应行高（justified rows）—— 按真实比例排，但不留空洞

**问题**：上一节把卡片改成按真实比例之后，排布还是 CSS grid **按行对齐** —— 一行的高度取这行里
最高的那张，于是横图（矮）下面必然空出一大片。这**不是**边角情况：实测库里横图占一半，
`垃圾桶` / `新世界` / `里世界` / `表世界` 那几个壁纸来源更是 100% 横的（一万四千多张），
所以是满屏空洞。用户的原话是"间隔太大，我不能接受"。

**做法**：换成 Flickr / Google 相册 / 苹果照片那套 **justified rows**
（`src/composables/useJustifiedRows.js`，算法是纯函数 `buildRows`，DOM 只在 composable 里）：

| 步骤 | 说明 |
|---|---|
| 贪心分行 | 一张张往当前行塞，按"目标行高"估铺开要多少宽，超过容器宽度就把这一行定下来 |
| 按比例铺满 | 定下来的行重新分配宽度让左右正好贴边 —— 行高因此略微浮动，这正是它好看的原因 |
| 不裁图 | 每张宽度 = 行高 × 它自己的宽高比，所以**一张图都不用裁** —— 两条约束同时成立 |

- **目标行高不是拍脑袋**：取 `竖图宽度 ≈ 原来的 --grid-min(150px)` → `targetH = 150 × 16/9 ≈ 267px`。
  于是**竖图的观感与改动前完全一致**（150×267），横图自动变宽变完整（约 500×280）。
- **末行不强行铺满**：按目标行高排开占不到容器 `3/4` 就左对齐、保持目标行高 ——
  强行铺满会把末尾那一两张拉成巨图。
- **行高夹在 120–600px**：防超宽全景图 / 极端窄图把一行拉爆。
- **拿不到尺寸的图**（老库没回填 / 文件头读不出来）按 9/16 参与排版，与卡片自身的回落一致 ——
  "新特性对老数据的行为不变"这条在**布局层**也成立。
- 宽度由 `ResizeObserver` 量**网格元素自己**的 `clientWidth`（窗口缩放 / 无限滚动追加时重排）。
  ⚠️ 回调必须**延到下一帧**再写响应式状态，否则浏览器会报
  `ResizeObserver loop completed with undelivered notifications` —— 见"第 15 个坑"。

CSS 侧是 `.grid.jrows`（flex 列）+ `.jrow`（flex 行）+ `.jcell`（宽度由 JS 给、高度用内联 `--img-h`）。
**文字区必须固定高度**（`.tags` 28px、`.foot` 20px；keys 模式 42px）—— 行内每张卡的图高一致，
但标签换行会让卡片总高不一致，行与行之间就豁牙了。

#### 3. 安全模式（按标签集合隐藏）—— 开关铺到每一个能看到图的页面

> 口径与集合的定义见本节下半段；2026-09-23 补的是"**入口铺开**"。

原来只有**标签页**一个入口，用户要的是"每个能看到图片的地方都有开关、打开就一键过滤掉"。
现在是 `TvSafetyToggle` 组件（🛡 开关 + ⚙ 设置台 + 隐藏计数），落在：
看板 / 扫描页（文件夹库那层 + 图片那层**各一个**）/ 系列页（顶栏 + 图片工具条）/ 标签页 /
标签图片页 / 收藏页 / 购物车页（含抽屉，`icon-only`）/ 详情页 —— e2e 逐页点数。

另外三处下沉（都是为了让"看起来"和"数出来"一致）：

- 过滤从**卡片层**（`v-if="!hidden"`）下沉到**网格层**（`TvImageGrid` 的 `filterItems`）——
  于是页脚那句「已经到底了（共 N 张）」里的 N 是**过滤后**的真实张数；光箱的翻页序列也从
  同一份过滤结果取（各视图的 `imgPaths` 由 `shown` 派生），不会出现"网格里看不见、翻页却翻到它"。
- 全被藏掉时给**明确提示**（"N 张都被安全模式隐藏了 —— 在工具栏关掉它就能看到"）——
  否则看起来像"搜不到"，用户会以为搜索坏了。
- 关掉时 `filterItems` **返回同一个数组引用**（不是新数组）—— 否则下游会误判"数据变了"，
  白跑一轮重查。

**库外图**（扫描页那些没进库、没有 `unsafe` 标记的）走前端**镜像判定**
（`src/utils/safetyMatch.js`，与 `core/safety.js` 同一套 `compileRules` / `hitOne`），
`test:visual` 里有成对的**交叉验证**（含大小写、`*_penetration` / `*_lingerie` 通配、不误伤），
保证两边判定不会分叉。镜像用 `WeakMap` 按"标签数组引用 + 代次"记忆，不会每帧重算。

按"标签集合"判定，两档：

| 档 | 收录 | 实测会隐藏 |
|---|---|---|
| `core` | 明确裸露 / 性行为（19 条：`nude`、`nipples`、`pussy`、`sex` …） | 45,366 张（58.4%） |
| `edge` | 在 core 之上再加擦边 / 内衣 / 打码（+19 条：`underwear`、`cleavage`、`ass` …） | 69,919 张（90.0%） |

⚠️ **`breasts` / `large_breasts` 这类"体型"标签刻意不收录** —— 实测 `breasts` 命中
**77,437 张（93%）**，收进去等于把库藏掉九成。同理 `thighhighs`（21,965）、
`cleavage`（20,019）、`underwear`（20,065）、`ass`（19,179）在二次元图里几乎是标配，
只进 `edge`、不进 `core`。

- **默认关闭**：core 档就会藏掉近六成图，这种东西不能默认开；配置文件坏了也一律回落"关"
  （宁可不过滤，也不要突然少一半图）。
- 只做**展示层**过滤（看板 / 列表的卡片），不动库、不改统计口径、不改导出内容。
- 集合放 `data/safety_tags.txt`（`[core]` / `[edge]` 两段 + 注释，首次使用自动写出，
  可直接编辑），开关与档位放 `data/safety.json`（默认 `{"on":false,"level":"core"}`）。
- 界面入口在**标签页**的「🛡 安全模式」：开关 / 换档 / 逐条移出 / 追加标签 / 直接改原文，
  改完立刻重算（`recomputeSafety()`，八万条约一两百毫秒），前端只 `bumpEpoch()` 重查一次。
- 判定在**读数据集时算一次**（`pushRecord`）并挂在每条记录上（`unsafe: 0/1/2`），
  前端切开关只做数值比较，不重载数据集。

#### 4. 开关上那个数字：跟着当前来源走 + 关着也显示

> 用户 2026-09-23 的追加反馈：
> 「这边的数字能不能**根据不同的来源**显示被隐藏的数字」
> 「然后这个数字我**不点这个按钮好像就默认是 0**」

原来那个 `−45,603` 是**整个库**的统计（主进程读数据集时算好的 `coreHit`）—— 进哪个来源、
翻到哪一页都是同一个大数，对"这个来源到底藏了多少张"没有回答能力；而且它挂在
`v-if="safety.on"` 上，**关掉时直接消失**，所以用户看到的正是"不点它就像 0"。

现在两处都改了：

| 谁 | 数字从哪来 |
|---|---|
| 看板 / 系列页 / 标签图片页 | `feed.unsafe` —— 后端在**同一次查询**里顺带算的 `{core, edge}` |
| 扫描页（图片层） | `safety.countHits(rawItems)` —— 当前**文件夹**那批图 |
| 收藏页 | `safety.countHits(favRaw)` —— 当前过滤后的收藏 |
| 标签页 / 详情页 / 扫描页的**文件夹列表层** | 不传 → 回落整个库，title 里写明"整个库"，不冒充当前范围 |

三处关键设计：

- **必须后端算**：看板 / 系列 / 标签图片三页走的是**分页**的 `useImageFeed`，前端手里只有
  已加载的几十张 —— 拿它算出来的数字会随着往下滚不断变大，看着像在跳。后端 `doSearch` 里的
  `results` 是**筛选 + 排序后的全量**，一次遍历就准；`unsafeCountOf` 用 `WeakMap` 按
  "结果数组引用"记忆 —— `searchCached` 命中时返回同一个数组、`applySort` 是 in-place 的，
  所以翻页是白捡的，不会每次重扫几万条。
- **计数与开关无关**：`countHits` 刻意**不看 `on`** —— 这正是"没打开也该知道会少多少张"。
  口径与主进程的 `coreHit` / `edgeHit` 逐字一致（core 档藏 `unsafe=1`；edge 档 `1` 和 `2`
  都藏），`test:visual` 里拿 `hiddenAt` **逐条对了一遍** —— 这个数字算错不会崩，只会撒谎。
- **关着也显示**（淡色）：开着用 `--accent`、关着用 `--muted`，title 分别是"已隐藏 N 张" /
  "有 N 张命中「core」档 · 打开后被隐藏"。数字为 0 时不渲染（`−0` 是噪声）。

e2e 为它造了个**专门的夹具夹**（3 张图，其中一张的提示词从 `smile` 改成 `nude`）：

- 开关**关着**时数字就是 **1** —— 若它还是全库统计，沙箱库里是四万多，**不可能是 1**，
  所以这一条本身就证明了"跟着当前来源走"；
- 打开后网格**正好少掉 1 张**（数字不撒谎）；
- 换到一个**干净**的文件夹 → 数字整个消失，再证一次它是跟着来源变的。

> 造这个夹具时踩到一个点：PNG 的文本块**改了必须重算长度和 CRC32**，直接改字节会得到坏图
> （缩略图加载失败，反而把控制台断言顶红）。Node ≥ 20.15 自带 `zlib.crc32`，不用自己写表。

**顺带挖出一个真 bug**：做这个数字时才发现 `safety.load()` 原来**只在设置台被打开时**调用 ——
没打开过设置台（以及每次重启之后）的用户手里是**空规则**，于是**扫描页 / 收藏页的安全模式
一直是空转的**（库内页面用的是主进程算好的 `unsafe` 字段，所以看不出来）。
已改成 store 首次被取用就自动加载，详见踩坑第 21 条。

### 2026-09-23 扫描页排序：记住选择 + 8 种排序

用户的两条诉求：**"每次进去都要点一下排序"**（要求记住），以及**"增加按时间排序，以及其他的排序方式"**。

**记住**：排序值进偏好仓库 `usePrefsStore`（localStorage，键名登记在 `src/utils/lskey.js`），
四个地方**各存各的**（`sortHome` / `sortScan` / `sortSeries` / `sortTagImgs`）——
共用一个键的话，"在扫描页调成按时间"会顺手把看板的顺序也改掉。取值一律过白名单
（`SORT_OK` + `pickSort`）回落默认，防止手改 localStorage 或旧版本遗留的坏值把界面搞成空列表。

**扫描页现在有 8 种排序**：

| 值 | 含义 | 说明 |
|---|---|---|
| `name` / `name_desc` | 文件名 A-Z / Z-A | 用 `Intl.Collator({numeric:true})` —— 默认的字符串比较下 `10.png` 会排在 `2.png` 前面，`0001…9999` 这种命名看着就是乱的 |
| `folder` | 按子文件夹 | 先按所在文件夹，组内再按文件名 |
| `time_desc` / `time_asc` | 修改时间 新→旧 / 旧→新 | |
| `size_desc` / `size_asc` | 文件大小 大→小 / 小→大 | |
| `tags_desc` | 标签数 多→少 | |

两个实现要点：

- **`mtime` / `size` 是"白捡"的**：`electron/core/scan.js` 里 `statSync` 的结果本来就在 `statMap`
  里（用来判"有没有变过"），顺手把 `mtime` / `size` 放进 item 即可，**没有多一次 stat**。
- **排序全在前端做**：扫描页的对象是**库外图**（库里根本没有行），走不到数据集那条路，
  所以 `cmpOf(mode)` 在 `sortedItems` 里排；而且**主键相同的再用文件名兜底** ——
  同 `mtime` / 同大小的一批图若不兜底，每次刷新顺序都会变，看着像在跳。
  `sortedItems` 末尾还要过一遍 `safety.filterItems`（安全模式只过滤展示，不改排序结果）。
  兜底是可以**看见**的：e2e 的夹具里有两张同为 437 字节，于是"按大小 大→小"**不是**
  "小→大"的严格逆序 —— 并列的那一对在两个方向里都保持文件名升序。这条本身就是"兜底真的生效"的证据。

### 2026-09-23 尺寸链路：扫描页/收藏页的「横图显示为竖图」

用户报：「现在的网格布局方案有bug，横图会显示为竖图」。

**根因不在布局算法**（算法有 test:visual 的几何断言、e2e 还看板上量真实几何守着），
而在**数据**：扫描页的对象全是**库外图**（库里根本没有行），而 `scan.js` 组装 item 时
只带了 `path / name / tags / source / folder / mtime / size` —— **独独漏了 `px_w / px_h`**。
前端拿不到尺寸就回落 9/16，于是每个格子都按竖图算宽，横图被 `object-fit: cover`
裁成竖条。而且**一个错都不报**：尺寸的语义是「有就用、没有就回落」，静默的。

看板 / 系列 / 标签图片三页没事 —— 它们走数据集记录（`readRecords` 是带尺寸的）。
**收藏页**同一个病：收藏记录是 `{path, name, tags, at}` 的快照，也没有尺寸。

#### 修法：把「尺寸」收成一条统一入口

新增 `electron/core/dims.js` 的 `dimsForPaths(paths)`，按代价从小到大两条来源：

1. **内存数据集**（`ds.byPath`，O(1)）：登记进库的图直接拿到尺寸，**一次磁盘 I/O 都不用**。
   八万条记录的 Map 查一次是几十纳秒，比读一次文件头便宜好几个数量级。
2. **读文件头**（`imgsize.readImageSize`，4KB/张）：只对库里没有的图做，
   批量**跑在 worker 线程**里（几千张同步读会把主进程事件循环占死 = 界面卡死）。

认不出的给 `null`，调用方回落 9/16 —— **绝不猜**。
刻意**不做进程内记忆**：同一个路径的文件可能被换掉（Syncthing 同步），记住旧尺寸就会一直用错的。
要缓存就由调用方按 `(路径, mtime, size)` 自己存。

`parseInWorker / sizeInWorker` 顺带从 `scan.js` 拆到新的 `electron/core/imgWorker.js` ——
`dims.js` 也要用它，留在 `scan.js` 里就成了 `scan → dims → scan` 的循环引用。
`scan.js` 原样再导出一次，`ingest.js` 那行 import 一行都不用改。

#### 扫描页：尺寸跟**增量缓存**一起失效

`scan.js` 组装完 item 后补尺寸，两条路：

- 持久缓存里已有 `w/h` → **白捡**（`w/h` 与 `mtime / size` 一起存，文件改了自动重读）；
- 没有 → 批量读文件头，读完**写回 `scan_cache.json` 的条目**并标 `changed`。

于是「首扫读一遍，之后重扫是纯内存」，不会退化成「每次扫都读一遍」。
只对**将要返回的那批**做（超过 `limit` 被截掉的图前端根本看不到，不白读）。
进度条会切成「正在读取图片尺寸」—— 否则那几秒顶着「正在扫描元数据」的字样，看着像卡住。

#### 收藏页：收藏时顺手存 + 打开时补齐

- 收藏时（卡片 / 右键菜单）手里就有 item → 把 `px_w / px_h` 一起写进记录；
- 老记录没有 → 收藏页 `onMounted` 里 `fav.ensureDims()` 调一次 `dims:forPaths` 补齐，
  **在 `ready = true` 之前跑完**（那一处本来就是「找回跑完才渲染卡片」），所以不会出现
  「先按 9/16 渲染一帧、尺寸到了再整体重排」的跳动。结果写回记录并持久化，以后不再请求。

#### 夹具：得现编码「真的有横有竖」的图

`test-fixtures/scan-test/*.png` 全是 **1x1** 的占位图 —— 正方形，横竖都验不出来。
只改 IHDR 的宽高也不行：那会造出坏图（声称 320x180、实际 1 个像素），解码器报错，
缩略图加载失败反而把控制台断言顶红。所以新增 `scripts/testpng.mjs` 真编码 PNG：
签名 + IHDR + `prompt_text` 文本块 + IDAT + IEND，`padToSize()` 精确控制文件大小
（用尾部填充，不塞额外文本块 —— 那会让解析器多看到一个提示词来源）。

守这一条的两层断言：

- **test:visual**：`dimsForPaths` 的优先级（数据集那条用一个**文件并不存在**的假记录证明
  「零 I/O 也拿得到」）+ `scanFolder` 返回的 item 真的带 `320x180` / `180x320` +
  尺寸**写进了 `scan_cache.json` 的条目**（否则「首扫慢」会变成「每次扫都慢」）。
- **e2e 11g**：造 3 张真图进扫描页，量**页面上的真实几何** —— 每张卡图片框的宽高比
  必须等于它自己文件头里的比例。**一个常量比例不可能同时满足那三张**，
  最后一条断言就是专门堵「常量也能过」的，所以这几条不可伪造。

### 2026-09-24 右键「复制图片到剪贴板」修复 + 「用其他程序打开…」

**用户报的现象**：右键菜单里的「🖼️ 复制图片到剪贴板」**点了完全没反应，粘贴不出来**。

**根因（实测，不是推测）**：Electron 44.3.0 的主进程 `clipboard` 已经换成 W3C 语义，
`Object.keys(clipboard)` 只有 **`clear / has / read / readText / write / writeText`**
—— **`writeImage` 这个方法不存在了**。而原来的实现是：

```js
try { clipboard.writeImage(nativeImage.createFromPath(imgPath)) } catch { /* 图片读不到就算了 */ }
```

必然抛 `TypeError: clipboard.writeImage is not a function`，被那个**空 catch** 吞掉 ⇒
每一次点都这样、**跟图片格式和大小都无关、连一句提示都没有**。这就是"失效"的全部原因。

> 顺带发现的两件事（都会让"写剪贴板"这件事变得比看起来难）：
> · `clipboard.write()` 只收 `[ClipboardItem]`，而且**异步 reject**
>   （`clipboard.write expects an array of ClipboardItem`）—— `try/catch` 接不住；
> · `has()` / `read()` 返回 **Promise**；`read('image/png')` 也**不是** Buffer，
>   拿它去比字节会得到 1 字节/`[ClipboardItem {}]` 这种结果。

**改法**（新增 `electron/core/clipboardImage.js`）：

| 环节 | 做法 |
|---|---|
| 拿尺寸 | `planCopy()` 只读**文件头**（复用 `imgsize.js`），不解码 —— 好在动手前就把尺寸报给界面 |
| 先报进度 | `copyImageWithNotice()` **先**推 `app:toast`「正在复制图像（宽×高）…」+ 让出一帧，**再**进同步段 |
| 真写 | `clipboard.write([new ClipboardItem({'image/png': Blob})])`，带 20s 死线（实测大图写入要 1.7s，死线只能抓"永不返回"） |
| 自证 | 回读 `clipboard.has('image/png')`，**读不到就报失败**（"write 没报错"≠"剪贴板里真有一张图"） |
| 不静默 | 空图（webp）/ 文件不在 / 写失败 / 回读失败，全部返回 `{ok:false, error}` 由界面弹 toast |

同一轮还加了右键菜单的「🗂️ 用其他程序打开…」（`rundll32.exe shell32.dll,OpenAs_RunDLL`），
见下面「打开方式」一节。

#### 实测数字（真机 + 真图 + koffi 交叉核对）

开发期的**一次性探针**（放在 `per-monitor-wallpaper` 仓库的 `tools/tmp/` 下跑：
借那边的 koffi 才能量 `GlobalSize`，并**开跑拍快照、结束按字节还原**剪贴板；

| 图 | 编码 | 写入 | 端到端 | koffi 回读系统剪贴板 |

**大图为什么慢、以及为什么没顺手"优化"掉**：慢的那 5 秒是 `nativeImage.toPNG()`，

都不适合默默替用户决定：

- **koffi 直写 CF_DIBV5**（跳过 PNG 编码，同机 `per-monitor-wallpaper` 已验证 ~1s、无损）

- **自己套 BMP 壳子塞给 `write()`** —— **实测行不通**：Chromium 只解 PNG / JPEG
  **内容**，喂真 BMP 会得到**空剪贴板**（而且 `write()` 立刻 resolve、不报错；
  拿 JPEG 字节贴 `image/bmp` 反而成功 —— 说明 **MIME 标签不参与判断，按内容嗅探**）。

`toJPEG` / 真 BMP 这两条都测过了，数字在上面；要不要换是个产品决定，不是 bug 修复。

## 二十六个踩过的坑（已修，留档备忘）

### 1. 窗口比数据先到，首屏数字偏小

窗口是**在数据集加载之前**就渲染出来的（否则会有十几秒白屏）。于是渲染进程挂载
首页时会立刻发 `stats:get` / `search:do` —— 那时 `ds.records` 只填了一半，
返回的快照自然偏小（实测显示 2,599 而不是 71,214，来源计数几乎全是 0），
而渲染进程拿到就存进 store，**之后再也不会自己刷新**，得手动点一次「搜索」才恢复。

修法两层：
- 主进程：数据类 channel 一律先 `await whenReady()` 再算（见 `app-state.js`）；
  加载结束后再统一作废派生缓存一次。
- 渲染进程：`useAppStore` 增加 `epoch`，数据从 loading 变 ready 就 +1，
  首页 watch 它重跑一次初始查询（这样菜单里的「重新加载数据」也能自动刷新已挂载的视图）。

### 2. 固定调试端口会连到旧实例

e2e 原本用固定端口 9223。只要机器上还有一份之前手工起的实例在监听，
`findPage()` 就会连到**那只旧窗口**上：初始路由不对、卡片数是别的视图的数字、
找不到首页的输入框……一路断言全挂，而新起的进程因为单实例锁已经退出了。
表现完全是"代码有问题"，实际代码没问题。

修法：每次随机取空闲端口 + 独立 userData + 校验连上的 URL 属于本项目 +
主进程早退就立刻报错。**看到"测试莫名其妙全挂"先怀疑连错实例。**

### 3. 构建产物不许攒着（否则构建直接失败）

`vite build` 默认 `emptyOutDir: true`：每次构建先把 `dist/` 清空重建。
在本机这撞上了执行环境的批量删除保护 —— 要删的文件超过 50 个就报
`SAFE_DELETE_BULK_CONFIRM_REQUIRED`，构建直接红掉。

修法是**让构建不再需要删除**：`emptyOutDir: false` + 关掉文件名内容哈希
（`assets/[name].js` 固定名）。对本机 `file://` 加载的 Electron 应用来说，
内容哈希本来就没有价值 —— 没有 HTTP 缓存要绕，没有"必须换文件名"的理由。
改完之后每次构建是覆盖而不是先删后建，`dist/assets` 恒为 24 个文件，
连跑多次也不会变大（已实测）。历史上带哈希的旧产物用 `npm run prune:dist` 收拾。

### 4. 模板引用了未定义的绑定 —— **在生产构建里完全静默**

做「滚轮翻页 + 文件夹库」时踩的，值得单独留档，因为它是**最贵的一类 bug**：
不报错、不崩溃、连警告都没有，表现只是"某个按钮不出现"，看着像功能没做。

两个实例，都是同一个成因：

| 文件 | 模板里写了 | 实际情况 | 后果 |
|---|---|---|---|
| `HomeView` / `SeriesView` / `TagsView` | `lb.open(it.path, { list: imgPaths })` | 三个视图都**没定义 `imgPaths`**（只有 `ScanView` 定义了） | 传进去是 `undefined` → 光箱不知道"下一张是谁" → 翻页箭头/滚轮/方向键全都不出现 |
| `SeriesView` | `@load-more="onLoadMore"` | 没定义（应该是 `imgFeed.loadMore`） | **无限滚动一直是坏的**，滚到底永远不加载 |

**为什么没有立刻发现**：`<script setup>` 编译出来取不到的名字是 `$setup.xxx` → `undefined`，
不抛错；而开发期那句
`Property "imgPaths" was accessed during render but is not defined`
带 `__DEV__` 判断，`vite build` 会整段摇掉 —— 所以 e2e 里
「运行期无 Vue 警告」这条断言根本拦不住它。更糟的是当时那条无限滚动断言写的是
`after >= before + 0`（等于不比），于是 bug 又藏了一轮。

**修法（两层）**：

1. 代码：三个视图补上 `imgPaths` + `watch` 同步；`onLoadMore` → `imgFeed.loadMore`；
   断言改成 `after > before`。
2. **加了静态守卫 `scripts/check-templates.mjs`**，已接进 `npm run check` / `build`。
   原理很直接：Vue 编译器在 `prefixIdentifiers` 下，**能解析到 setup 绑定**的名字编译成
   `$setup.xxx`，**解析不到**的编译成 `_ctx.xxx`。所以拿 `compileScript` 给出的 `bindings`
   当 `bindingMetadata` 去编译模板，再扫产物里有没有 `_ctx.<名字>`，就能精确点名。
   几秒钟跑完，不用起 Electron（实测：故意把 `imgPaths` 写成 `imgPathsTYPO`，
   立刻报 `src/views/HomeView.vue -> 模板引用了未定义的名字 「imgPathsTYPO」（.vue 第 333 行）`）。

### 5. 测试自己不是幂等的（第二次跑必挂）

`e2e` 第一次跑 68/68 全绿，**第二次跑必挂一条**：`文件夹库: 首次进入是空列表 — 1 张`。
原因不是代码 —— 是上一轮测试把「扫描页收藏夹」`scan_folders.json` 写进数据副本，
留下的那条记录让"首次进入应该是空的"这个前提不再成立。

同理，首页大图预览那条断言原本假设"第一张图一定有角色/系列标签"，
但**首页默认排序是随机**（`sort = ref('random')` + 随机 seed），
所以第一张每启动一次都不一样 —— 实测第一遍 0 行 FAIL、第二遍 2 行 PASS。

修法：
- `harness` 每轮把 `scan_folders.json` **覆盖成空档**（只写不删，不碰批量删除保护）；
- 光箱断言改成**先问数据、再对 UI**：用 `lightbox:data` 查出这张图按定义该有几行，
  不满足就顺着列表往后翻（顺便验证翻页真的在换图），断言变成"渲染行数 == 数据项数"。

**判据是连跑两遍**：现在 71/71 × 2 全绿。只跑一遍就宣称通过的测试，等于没测。

### 6. e2e 的「数据隔离」曾经是失效的 —— 测试一直在读写用户的真实数据

`harness.ensureWorkDir()` 的注释写着「测试怎么改都污染不到用户真实积累的黑名单/购物车」，
但 2026-09-19 实测发现**这句承诺根本不成立**：`.e2e-work/userdata/` 里残留着一份早期排查脚本
写的 `settings.json`，里面 `dataDir` 指向**真实数据目录**。而 `workspace.js` 的解析优先级是

```
settings.json  >  TV_DATA_DIR  >  <userData>/data
```

`e2e.mjs` spawn 时只传了 `TV_DATA_DIR` —— 于是被那份 settings.json **悄悄地压掉了**。
后果是双重的，而且都很隐蔽：

- 测试写的 ban 标签 / 购物车 / 结算历史**全落在用户真实数据里**；
- `harness` 辛辛苦苦「每轮把 `scan_folders.json` 覆盖成空档」也没生效（它重置的是副本）。

**为什么不容易发现**：日志里只打一行 `[ok] dataDir=...\data` —— 复制出来的副本和真实目录
在日志里长得几乎一样，不逐字比对根本看不出来。

**修法**：隔离不能只靠环境变量，`ensureWorkDir()` 现在会**显式写**一份
`<userData>/settings.json`，把 `dataDir` 钉死到副本上（写，不删）。同时补上
`character_library.json` —— 少了它，扫描页的 key_tags/角色高亮、系列页的角色识别
都会降级（实测系列数从 386 掉到 244，`charLib` 直接 ENOENT），那批断言等于没测到真实路径。

**教训**：测试的隔离性必须**自己有一条断言**（或至少显式写死关键路径），
靠"我传了环境变量"是不够的 —— 只要优先级链上还有更高优先级的来源，隔离就是纸糊的。

### 7. 「导出内容里的标签」和「数据集里的标签」不是同一个写法 —— 拿前者去 ban 是**静默空操作**

2026-09-22，导出预设功能写完、手工验过，但 e2e 有 **4 条断言**报「ban 之后自动导出没被触发」，
而**手动导出一切正常**。现象看起来完全指向主进程里的就绪守卫（`phase !== 'ready'` 就不导）。

先跑探针把 `app:status`/排程回执/预设 `lastError` 全抓回来，结论是**守卫是无辜的**：
`phase=ready`、`scheduled=true`、`autoCount=1`、`lastTrigger=auto` —— 链路每一环都通。

真因在**形态**上：

```
导出文件里看到的      tags.db 里存的        实测
looking at viewer  ←→ looking_at_viewer   68016 张
open mouth         ←→ open_mouth          36143 张
```

`buildExport` 默认 `spaces=true`，会把每个标签的 `_` 换成空格；而 `isBlockedFast()`
拿**下划线形态**的标签去比对，**不做空格→下划线归一**。于是测试从导出内容里挑 token
（拿到的是空格形态）原样丢给 `blacklist:toggle`，黑名单里就多了一条
`looking at viewer` —— **这条规则永远不可能命中**。

致命的地方在于：`afterBlacklistChange` 只比对**黑名单文本指纹**。文本确实变了，所以
`scheduled=true`、自动导出照跑、落盘也成功，唯独**导出内容逐字节不变** —— 断言看到的
就是"自动导出没被触发"。手动导出之所以正常，是因为它不经过这一步。

**修法**：凡是拿导出 token 去操作**数据侧**（黑名单）的地方，一律先
`.replace(/ /g, '_')` 转回数据集形态；比对"是否已被 ban"也要用同一个形态
（原来用空格形态比，对多词标签永远比不中，白名单判断也是失效的）。

**教训**：同一个概念在系统里存在**两种书写形态**时，"格式转换"必须发生在**边界**上，
而且要有断言把这个边界钉住 —— 否则它会以一种"看起来像另一个 bug"的方式炸掉，
（本例里伪装成了"就绪守卫把导出挡了"）。留档证据：`.e2e-work/probe-tag-form.mjs`。

### 8. Windows 上 `fs.renameSync` 会**因为别人在读而失败** —— 一次 EPERM 就把整次导出丢掉

原子替换（写 `.tmp` 再 rename）在 POSIX 上是个"永不等、永不失败"的操作，于是很容易
写成裸的一行 `fs.renameSync(tmp, full)`。Windows 上不是：替换**已有**目标时，只要
对方句柄没带 `FILE_SHARE_DELETE`，这次 rename 直接 `EPERM`。

实测（2026-09-22，自动导出 42MB 目标文件）：

```
EPERM: operation not permitted, rename
  '...\preset-e2e.txt.tmp18424' -> '...\preset-e2e.txt'
```

占住文件的通常是**刚写完就被扫一遍**的 Windows Defender / 搜索索引器。
后果比"报个错"严重得多：文件还是旧的（用户以为导过了），`.tmp` 也留在目录里
（而且下次用的是同一个 `.tmp<pid>` 名字，会被静默覆盖 —— 于是**连证据都不剩**）。

**修法**：`replaceFileWithRetry()` —— 瞬时错误（`EPERM`/`EACCES`/`EBUSY`）按
60/120/180/240ms 退避重试，仍失败则清掉 `.tmp` 再抛。测试侧也别帮着添乱：
轮询目标文件先比 `mtime+size`，**只在真变了之后**才读 42MB 全文。

**教训**：跨平台代码里，"原子操作"只是语义上的原子性，**不代表它会成功**；
在 Windows 上要默认"任何人都可能正拿着这个文件"，并把瞬时失败当成常态来处理。

### 9. `An object could not be cloned.` —— 把 Vue 的响应式代理递过了 IPC 桥

2026-09-22，导出预设上线后用户点「💾 创建预设」直接报这句，**一条都存不进去**；
而同一时刻 e2e 是 **180/180 全绿**的。两件事都是真的，见最后一节"为什么测试没抓到"。

**根因**：`ipcRenderer.invoke` 走结构化克隆，而 **Proxy 一律克隆不了**。
Vue 的 `reactive()` / `ref().value` 取出来的东西整体是 Proxy，
更坑的是**嵌套**：`{ ...p, params: p.params }` 展开一层也救不了 ——
`p.params` 仍是代理，连里面的 `params.source` 数组还是代理。
本仓库的两个触发点都在导出预设弹窗：`save()` 传 `f.params`、
列表上的开关传 `{ ...p, auto: v }`。

**先分层再动手**（别一上来就改 preload）：拿一个**未授权 channel** 各打一发，看拿到谁家的报错 ——

| 调用 | 返回 |
|---|---|
| `invoke('no:such:channel', {a:1})` | `未授权的 channel: ...`（我们自己的白名单检查跑到了） |
| `invoke('no:such:channel', new Proxy({a:1},{}))` | `An object could not be cloned.`（白名单**没轮到**） |

抛点在 **contextBridge 参数编组那一层**，早于 preload 里自己的函数体 ——
**改 preload 没用，必须在上游（渲染进程）把代理拆掉**。
不用起 Electron 就能复现：`structuredClone(new Proxy({a:1},{}))` 直接抛，
`structuredClone({p: new Proxy({},{})})` 同样抛（嵌套也算）。

**修法**：在"渲染进程访问主进程的唯一入口"`src/utils/api.js` 的 `call()` 里，
传给 `tv.invoke` 之前统一过一遍 `toPlain()` 深拆：数组/纯对象递归重建，
`Date`/`Map`/`Set`/`Buffer`/TypedArray/类实例**原样放行**（结构化克隆本来就支持），
函数**原样放行**（让它照旧响亮地报错，别在这里静默吞掉），
`WeakMap` 兜循环引用，遇到 `__v_isRef` 先取 `.value`。
注意别拆过头：`JSON.parse(JSON.stringify())` 也能解克隆问题，但会丢 `undefined`、`Date` 变字符串。

**为什么测试没抓到（最贵的一条）**：那 180 条断言全是**拿纯对象直接打 `window.tv.invoke`** ——
数据从主进程回来本来就是纯 JSON，测试又从不经过 Vue 的响应式状态，
于是"在界面里点保存"这条真实路径**一行都没被覆盖**。
补的 6 条断言因此刻意**走真实界面**：点 `📤 预设导出` → `＋ 新建预设` →
用原生 setter 填两个输入框并派发 `input`（Vue 的 `v-model` 认这个事件）→ 点 `💾 创建预设` →
断言表单无报错、预设落库、`params` 逐字段完好、列表上的 auto 开关也能存回去，
最后删掉不留残留。

**验证方式是 A/B**：先在**旧 bundle**上跑同一段探针留下失败证据
（`formErr:"An object could not be cloned."` · `backToList:false` · 一条没存进去），
`npm run build` 之后再跑，对照成功态。只有"新代码不报错"不算证明 —— 得证明**旧代码会报错**。

**教训**：e2e 全绿 ≠ 用户点得动。凡"用户在界面上点一下"的链路，
至少要有一条断言真的去点那一下；只测 IPC 等于只测了一半。

### 10. `is-switch` 的开关**没有 `<input>`** —— 照搬"点 `input.checked`"拿到的是 `null`

`TvCheckbox` 在 `is-switch` 模式下渲染的是
`<label class="tv-check"><span class="track"><span class="knob"/></span><span class="txt">…</span></label>`：
**根本没有 `<input type="checkbox">`** —— 状态表达在 `.tv-check.on` 这个类上，
点击处理器挂在 `<label>` 的 `@click.prevent`。只有**非**开关模式才真的渲染 `<input>`。

给来源页加第三个开关时，断言顺手写成 `items[i].querySelector('input').click()`，
当场 `TypeError: Cannot read properties of null (reading 'click')`，
整轮 e2e 从这句中断（`161/162 通过, 1 失败`，后面的断言一条都没跑）。

**正确写法**：用仓库既有的 `__t.clickText(sel, '自动反推')` 点 `<label>`，
读状态用 `classList.contains('on')` —— 而不是 `input.checked`。

**教训**：写"点界面"的断言前先看一眼组件的**真实 DOM**，别按"复选框就该有 input"的印象写。
另外这也说明 `test:ipc`（13 条全绿）在这类问题上是**帮不上忙**的 —— 它压根碰不到 DOM。

### 11. 一个**空字符串**能让整整一个来源在界面上隐身

`folders.label` 留空是**合法状态**（扫描页「添加文件夹」根本不传 label），界面上那个名字是
`decorate()` 用 `path.basename()` **临时合成**的 —— 于是"库里是空串"这件事在界面上**看不出来**。
而 `label` 恰好又是看板分组的键（`readRecords` 把它填进 `record.source`），
`sourceNameList` 里还写着一句 `WHERE as_source = 1 AND label <> ''`：新登记的目录于是
拿到了一个空来源名，它的图**计进「全部」、却没有自己的胶囊** —— 筛不到、也藏不掉。

实测现场：`表世界` 的 2970 张全挤在一个 `source=''` 的隐形分组里，「全部 85,474」与
8 颗胶囊之和 82,504 的差**正好是 2970**。复刻一句 SQL 就定位了。

**教训**：一个字段同时当"给人看的备注"和"给程序用的键"时，**它就不能是可空/可缺省的**。
要么在写侧保证非空，要么在读侧对**所有**消费者统一兜底 —— 而且两条读路径
（谁有哪些分组 / 每条记录属于哪个分组）必须共用同一份计算，分叉就会让两边对不上。
根治手法见「2026-09-23 来源名与移出来源」那节。

### 12. KeepAlive 的视图里，`onMounted` 拉出来的列表会**一直陈旧**

`ScanView` 在白名单里（这是 2026-09-19 特地为"切走再切回停在原地"加的），
代价是 **`onMounted` 一辈子只跑一次**。而扫描页那份文件夹列表的上游 —— `folders` 登记表 ——
现在是**来源页与扫描页共用的一张表**：在来源页把某个目录勾成「扫描夹」、或者把它移出/恢复，
切回扫描页看到的还是老清单，用户视角就是"我加了、它没反应"。

实测现场：e2e 里先 `folders:update {as_scan:true}` 再切到扫描页，那一堆断言里只有

**教训**：往 KeepAlive 白名单里放一个视图，等于承诺"它的数据不会在后台变"。

### 13. 两条**互不相干**的测试同时挂 —— 先去看主进程，别查测试

2026-09-23 加 `px_w/px_h` 时，`ipc.js` 里出现了**两行**从同一个模块 import 的语句
（原有的 `{ ds, tagPoolSize }` 与新增的 `{ ds, recomputeSafety }`）。ESM 对**重复绑定**
直接报 `SyntaxError: Identifier 'ds' has already been declared`。

现象很有误导性：`test:ipc` 报的就是这句（还算直白），而 `test:nodata` 报的是
**"CDP 端口没起来(port=1976)"** —— 因为 Electron 主进程**加载就崩了**，窗口根本没起。
两条测试看上去毫不相干，很容易分别去查测试本身。

**教训**：两个以上互不相干的用例**同时**挂、且报的是"起不来 / 端口没起 / 连不上"，

另外：`npm run check`（preflight）**不解析主进程语法**，查不出这种错；
`node --check <文件>` 能（它做的是 ESM 早期错误检查）。

### 14. "改了但没生效，而且不报错" —— 同一个出口的第二处

`search.js` 的出口原本写的是 `out[w++] = { path: r.path, tags: kept }` ——**手写字段列表**。
2026-09-23 卡片改成按真实比例渲染后，这个出口**没带上 `px_w/px_h`**：前端拿不到尺寸，
于是**所有**卡片悄悄回落到 9/16（横图又被裁成竖条），而且**一个错都不报** —— 控制台干净、
其余 218 条断言全绿，只有那条专盯比例的断言抓到了。同一处还漏了 `unsafe`
（安全模式会永远筛不掉任何东西）和 `source`（卡片上的来源角标消失）。

**教训**：出口如果必须"重建"对象（这里是 `tags` 要按排除词过滤后重写），就用**展开**
（`{ ...r, tags: kept }`）而不是手写字段列表 —— 以后给记录加字段会自动带出来。
这跟新列要加在 **`ADDITIVE_COLS`**（加进只跑一次的迁移 `applyV2Shape` 里，对早就迁完的
老库**永远不生效**、也不报错）是同一类问题：**改动的落点选错，就会静默失效**。
判断落点的方法只有一个 —— 去看那段代码**什么时候被执行**。

### 15. `ResizeObserver` 回调里同步改响应式状态 → 浏览器报 loop 警告，**而且这条警告不在 e2e 的错误断言里**

自适应行高靠 `ResizeObserver` 量容器宽度，回调里写 `width.value` → 触发重排，浏览器报：

```
ResizeObserver loop completed with undelivered notifications.
```

原因是 Vue 的组件更新在**微任务**里冲掉，而"投递 resize 观察"这一轮**之内**就会把微任务跑掉 ——
刚写下的 width 立刻引起又一次布局变更，浏览器判定这一轮没投递干净。
把量测推到**下一帧**（`requestAnimationFrame` 合并同帧多次通知）就正常了。

**最贵的部分是它藏在哪里**：这条警告**一个断言都没顶红** —— 227 条全绿，控制台那条断言写的还是 0 条。
因为它走的是**主进程转发**那条通道
（`electron/main.js` 的 `console-message` → `<ts> [render] <url>:<line> [error] …`），
而 e2e 的错误收集走的是 **CDP**（`Runtime.consoleAPICalled` / `Log.entryAdded`）——
**浏览器自己产生的消息只走前者**。所以"断言全绿"≠"控制台干净"。

**怎么发现的**：改完这轮顺手 `grep` 了一下日志里的 `ResizeObserver`，r1–r3 是 **0 条**、r4/r5 是 **7 条**
—— 一眼看出是这轮引入的。光看断言表格永远发现不了。

**两处都修**：① 根因 —— 回调改成 `measureNextFrame()`（下一帧、同帧去重）；
② 盲区 —— e2e 新增一条断言，把主进程转发那条通道也纳入检查（豁免口径与 CDP 那条完全一致）。
这条断言就是为这次这个 bug 加的。

### 16. `scoped` 样式的作用域是**组件文件**，不是元素 —— 同名类会在同一文件的两个用途之间串台

给扫描页的图片网格套上 `.grid.jrows`（定义在全局 `tokens.css`）之后，**文件夹网格的规则也命中了它**：
`ScanView.vue` 本地 `<style scoped>` 里那条 `.grid { display: grid; … }`。
因为 scoped 编译出来是给**该文件模板里的每个元素**都加同一个 `data-v-xxx` 属性 ——
两个网格都在这个文件里，属性一样，选择器拦不住。

后果是图片网格被套上 `display: grid`，**自适应行高的 flex 行布局整个失效**。

而且它是**权重相同、只看打包顺序**的定时炸弹：`.grid.jrows`（0,2,0）与 `.grid[data-v-x]`（0,2,0）
谁也不压谁，tokens.css 先进、组件样式后进 → 组件那条赢。

**修**：文件夹网格改名 `.grid.folders`（语义也更清楚），让图片网格只有一处定义。
**教训**：`scoped` 挡的是"**别的组件**的样式"，挡不住"**同一个文件里另一处**用了同一个类名"。
往一个已有本地类名的组件里引入全局类时，先看一眼这个文件里还有谁在用那个名字。

### 17. 一条 404 的豁免，必须能**证明**"它一定是陈旧数据"，不能放宽成"忽略 404"

沙箱库是从真实库 `VACUUM INTO` 拷来的，拷贝时点早于"应用最近一次同步"，于是库里留下一批
**文件早就不在磁盘上、却还 `gone=0`** 的行（实测 `Anima-Random` 一个来源就有 40 条）。
看板认为它存在 → 渲染卡片 → 请求缩略图 → 404。

这不是应用代码的 bug，是数据陈旧。但**不能**因此把控制台总闸改成"忽略 404" ——
那就把"删除图片后还在请求已进回收站的那张"这条真断言一起废掉了（那是本仓库花过大力气修的 bug）。

所以豁免写成**双条件**（`isStaleRecord`）：**路径在磁盘上确实不存在** ∧ **库里那行还在且 `gone=0`**，
两条同时成立才算陈旧数据；只满足"路径不存在"仍然报错。豁免范围也**只限被证明的那一条**，
不靠模式匹配。

**教训**：测试里"放行"和"忽略"是两回事。放行要说清楚**凭什么**（可复现的两条判据），
并且尽量收窄到具体对象；一旦放宽成"这类都不报"，那条断言就等于不存在了。

### 18. 一个 `location.reload()` 能把**别的**断言变成空断言 —— 顺序也是测试的一部分

测"扫描页排序重启后还记得"要用 `location.reload()`。但 9c 段把两个记录器装在**页面里**
（`window.__imgReq` / `window.__delBase`），reload 会把它们一起抹掉。而"幽灵请求总账"
读的正是这两个：

```js
const base = window.__delBase || ''            // => ''（reload 之后）
const hit = all.filter((r) => base && ...)     // => [] 恒成立
```

于是那条断言**照样绿，但已经不测任何东西**了 —— 比直接失败更危险，因为它会让人以为
"删除后不再请求已回收站图片"这件事仍然被守着。

修法是**排顺序**：幽灵请求断言 → 排序段（可以随便 reload）→ 控制台断言。
控制台那两条放在最后反而是**加强**：`cdp.errors` 与 `mainLog` 是 Node 侧累积的，
跑在最后就等于覆盖了整轮，**包括重载本身**产生的错误。

**教训**：凡是用到 reload / 跳转 / 重挂载的测试段，先问一句"它会把**前面**哪条断言的
观测点搬空"。观测点装在页面全局里的断言，只能排在破坏者**之前**。

**同一段里还踩到一个**：等待条件写成了"文件夹卡片数 > 0"，而列表里本来就有别的文件夹
（垃圾桶 / 桌面壁纸…）—— 条件**立刻**满足，新加的那张还没扫完就去找它，直接报"没找到卡片"。
**等待条件必须是"目标那一个出现"**，不能是"这一类非空"。

### 19. 模板里 `feed.unsafe` 传过去的是**一个 ref 对象**，不是它的值 —— 而且错得很安静

给开关加了 `counts` prop 之后，看板页写的是：

```html
<TvSafetyToggle :counts="feed.unsafe" />
```

`feed` 是 `useImageFeed()` 返回的**普通对象**（不是 `reactive`），`feed.unsafe` 是个 `ref`。
Vue 模板的"自动解包"只对 **setup 顶层暴露的 ref** 与 **reactive 对象的属性**生效 ——
普通对象里的 ref **不解包**。于是传进组件的 `counts` 是 `Ref { value: … }`，
组件里 `props.counts.core` 读出来是 `undefined`，`hasScope` 判成 `false`，
**数字悄悄回落成了"整个库"** —— 不报错、不警告、`npm run build` 也是绿的。

同一个文件里其实早有正确答案：`:results="feed.results.value"` —— 人家一直在写 `.value`。

**教训**：模板里从**普通对象**上取 ref，必须 `.value`；判断"传进来的到底是值还是 ref"，
最省事的办法是**在组件里断言类型**（`typeof props.counts?.core === 'number'` 才算数），
而不是假设 Vue 会帮你解包。

### 20. 改 PNG 里的文本块，必须重算长度与 CRC32

e2e 需要一张"真的会被安全模式隐藏"的夹具图，而现成夹具的提示词全是干净的。做法是把
某张图的提示词 `smile` 换成 `nude` —— 但 `nude` 比 `smile` 短，**chunk 长度变了**。

PNG 的每个块是 `长度(4) + 类型(4) + 数据 + CRC32(4)`，长度与 CRC 算的都是**块自己**的内容。
只改数据、不改这两个字段，文件就成了坏 PNG：缩略图加载失败 —— 而它的表现是**控制台多几条
错误**，最终以"运行期无 JS 异常"那条断言变红的形式出现，离真正的原因隔了好几层。

Node ≥ 20.15 自带 `zlib.crc32`，重算只要三行：

```js
const t = Buffer.from(type, 'latin1')
const c = Buffer.alloc(4); c.writeUInt32BE(crc32(Buffer.concat([t, data])) >>> 0)
```

（另一个细节：tEXt 块是 **latin-1**，读写都别用 utf8。）

### 21. 把"加载状态"交给一个弹窗去触发 —— 另一个入口就静默失效了

`safety.load()`（拉规则表 + 开关状态）原来**只在 `TvSafetyModal` 打开时**调用。也就是说：

> 从没打开过设置台的用户，store 里的 `core` / `edge` 是空数组 → `compileRules([])` 得到
> **空规则** → 库外图（扫描页那些 / 收藏里的标签快照）的安全判定**恒为 0**。
> 开关能点、能变色、toast 也照报，只是对那批图**一点作用都没有**，而且不报任何错。

库内图没事 —— 它们用的是主进程算好的 `unsafe` 字段，压根不走前端镜像那条路。于是：

- 库内页面看起来一切正常（确实在过滤）；
- 只有**扫描页 / 收藏页**是空转的，而那恰好是"用户特意来看图"的地方；
- 是自动化把它挖出来的：新加的"开关关着时那个数字应该是 1"读到了 0 ——
  数字只是**顺带暴露**的，真正坏掉的是过滤本身。

修法是**让状态的主人自己负责加载**（`ensureLoaded()`，store 首次被取用就发请求，
并发只发一次），而不是指望"某个 UI 恰好在某个时刻调用过 load"。

**教训**：store 里"只在一个地方被调用"的懒加载，只要还有**第二个入口**用同一份状态，
就必须在 store 内部兜底。自查方法很土但有效 —— 问一句"如果用户从不打开那个 UI，
这份状态会变成什么"。另外 `reload()` 等于把 store 全部重置，凡是依赖"前面某段已经
加载过"的假设，在 reload 之后都不成立（同第 18 条）。

### 22. 网格依赖的字段漏一个，就是**静默降级** —— 而且整个网格一起变样

「横图显示为竖图」就是这么来的：`scan.js` 组装 item 时漏了 `px_w / px_h`。
**不报错、不警告、构建也绿**，因为它走的是「有就用、没有就回落 9/16」这条路 ——
回落值本身是合理的行为，于是"数据没到位"和"这张图本来就没尺寸"长得一模一样。

两条自查：

- **凡是"改了渲染方式"的改动，都要顺着**数据**往回查一遍**：新渲染吃哪些字段？
  这些字段在**每一个**喂给它的数据源里都有吗？（这次有 5 个数据源，只有 2 个缺字段 ——
  而缺的恰好是用户日常用的那两个。）
- **回落到旧行为是好的设计，但它会掩盖"字段缺失"**。判据要写成
  「这一批里"有尺寸"的比例是多少」，而不是「有没有报错」。

顺带一个反直觉的点：**这类 bug 的位置常在最不像布局的地方**（这次在
`electron/core/scan.js` 的一行 `items.push`）。用户的描述是"网格布局方案有 bug"，
但布局算法一行都没错。

### 23. `migrate()` 是「读存储 → 新对象」的唯一入口 —— 新字段忘了抄，等于每次重启都丢掉

`useFavStore` 的 `migrate()` 把 localStorage 里的收藏记录**逐字段重建成新对象**
（只抄 `path / name / tags / at`）。给记录加 `px_w / px_h` 时如果只改 `toggle()`，
那么每张新收藏都能拿到尺寸、`persist()` 也写进去了 —— 但**下次启动**一读一抄，
尺寸又没了，于是每次打开收藏页都要重新补一遍（表现只是"有点慢 + 会闪一下"）。

**教训**：给持久化的记录加字段时，把「写入口」「读入口（重建对象那种）」「消费方」
当成一个整体改 —— 尤其是**写出去的形状和读回来重建的形状很容易不一致**。
（第 14 条是同一个道理的另一个面：同一个出口有两处。）判断读写形状是否一致，
最快的办法是 grep 那个字段名，看它在**几个地方**被列出来。

### 24. 新加一条 IPC 要同时改三处，漏一处就是「渲染端静默调不到」

主进程 `ipc.js` 注册 → `preload.cjs` 的 `CHANNELS` 白名单 → 前端 `call(...)`。
这次漏了中间那一步（白名单），而**预检抓到了**：
`ipc.js 注册了但 preload 白名单里没有(渲染进程调不到): dims:forPaths`。

值得记下来的是**为什么这个守卫值得留着**：漏了白名单，前端调过去只会
`reject`（`call` 的 catch 里通常吞掉），症状是"功能没反应"，**没有任何日志指向白名单**。
凡是"三处联动"的机制，都该让构建期把它变成一条必须过的检查。

### 25. e2e 断言「toast + 弹窗关闭」的时序：离场过渡比 toast 活得久

批量移动的断言（2026-09-23）第一版是「等网格更新 → 读 toast + 读弹窗关没关」。
实测 TvModal 的**离场过渡**（`<Transition>` + `v-if`）会让 `.mt-body` 在 DOM 里
多挂一截，而 toast 只活 2.6s —— 先等弹窗关完再去读 toast，读到的永远是空串
（r2 全场唯一一条 FAIL 就是它）。修法：**先抓会过期的（toast 用 waitFor 等它出现），
再等会迟到的（弹窗关闭）**。同段还有个反面教材：全删空之后，二级模板整个切到
「没有可显示的图片」分支，批量操作条跟着消失 —— 对"已消失的元素"断言计数必须
容错「元素不存在 = 也算归零」。

### 26. 一个空 `catch` 把「Electron 44 里 `clipboard.writeImage` 已经不存在」藏了不知道多久

右键「复制图片到剪贴板」**每次点都毫无反应、连提示都没有**。不是格式问题、不是大小问题：

```js
try { clipboard.writeImage(nativeImage.createFromPath(p)) } catch { /* 图片读不到就算了 */ }
//    ^ 这个方法在 Electron 44.3.0 的主进程里**不存在**（实测 keys 只有
//      clear/has/read/readText/write/writeText），必然抛 TypeError → 被吞 → 静默无操作
```

**为什么值得单独记一条**：吞异常让"调用了不存在的 API"看起来和"图片读不到"完全一样，
而这条路径**没有任何其它信号**（没有日志、没有 toast、剪贴板里留着上次的内容）。
凡是"点了应该有反应"的功能，`catch` 里必须**留下痕迹**（返回 error 交给界面弹提示）。

同一条路上还蹲着三个坑，一起记：

1. `clipboard.write()` 只收 `[ClipboardItem]`，而且**异步 reject** —— `try/catch` **接不住**
   （`clipboard.write expects an array of ClipboardItem`）。要么 `await` + `.catch`，要么加死线。
2. `has()` / `read()` 返回 **Promise**（W3C 语义）；`read('image/png')` **不是** Buffer，
   拿它比字节只会拿到 1 字节或 `[ClipboardItem {}]`。**能用的自证只有 `has()`**；
   要"载荷 ≥ 宽×高×4"这种硬证据，只能借 koffi 量 `GlobalSize`（开发期就是这么核对的，
   `read()` 那条路走不通：它取回的是**重编码**过的 PNG，4706B 写进去、17345B 读回来）。
3. Chromium 写剪贴板时按**内容**嗅探，**MIME 标签不参与判断**：拿 JPEG 字节贴
   `image/bmp` 照样成功；而喂**真 BMP** 会得到一个**空剪贴板且不报错**。
   ⇒ "换个小众格式能不能更快"这种想法，必须实测，别推理。

**顺带一条同类陷阱（与第 24 条对称）**：主进程 → 渲染层的**推送**是另一套白名单
（`preload.cjs` 的 `PUSH`），跟 `CHANNELS` 不是一回事。漏了它 `on()` 会**静默返回一个空退订函数**
（不报错、不警告），现象是"主进程明明发了、界面永远不动"。这次加 `app:toast` 就是三处一起改：
`ipc.js` 的 `PUSH_EVENTS` → `preload.cjs` 的 `PUSH` → `useAppStore.init()` 里的消费。

## 与旧版共存 / 回滚

- 旧版仍在 `../tag_viewer/`，`tag_viewer.bat start` 照旧可用。
- 新版只**读**数据文件；写操作（黑名单、元数据、购物车历史）写的是同一批文件，
  所以两边的规则/收藏是共享的 —— 这是刻意的，避免出现两套数据。
- 想回滚：直接用旧版启动脚本即可，新版没有改动任何原有文件格式。
- `.thumb_cache` 共用：新版按同样的哈希命名写入，旧版也能直接读到，不重复占空间。
- ⚠️ **例外：`tags_*.txt` 一归档，旧版就看不到来源了**（旧版靠扫这个目录里
  `tags_*.txt` 的文件名来认识来源，新版改读库里的 `folders` 表）。
  真要回滚到旧版，先 `npm run txt:archive:undo` 把它们移回来。
  反过来，新版**不依赖**这些 txt，归档之后照样用。
